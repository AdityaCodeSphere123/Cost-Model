\section{Summary}

A cost model for a Wayang operator predicts how much of each resource the operator uses: CPU time, memory, garbage collection (GC), disk I/O, data moved between processes or machines, and a fixed overhead per job. Every extra resource is another prediction target and another source of error, so we measured which ones actually matter. For each platform and operator we ran the operator inside a plan and subtracted the same plan without it, so every number below is what the operator itself adds. A resource is \hl{needed} when it is clearly above measurement noise and large relative to the operator's total cost; it is \hl{not needed} when it is negligible for every operator of the platform.

\textbf{Java}\vspace{-0.3em}\begin{itemize}\itemsep0pt
\item \hl{Needed:} CPU (FlatMap, ReduceBy, GroupBy, Sort, Join, Cartesian, TextFileSink); disk I/O (TextFileSink).
\item Only in some configurations: fixed per-job overhead (TextFileSink).
\item \hl{Not needed} (negligible for every operator): garbage collection.
\item \emph{Not assessed in this data} (not measured): memory.
\item Operators whose own cost is below measurement noise: Map, Filter, GlobalReduce, Count, UnionAll (a constant or a per-row cost from the source/sink is enough).
\end{itemize}

\textbf{Spark (single node)}\vspace{-0.3em}\begin{itemize}\itemsep0pt
\item \hl{Needed:} CPU (Map, FlatMap, ReduceBy, GroupBy, Distinct, Sort, Join, Cartesian); memory (GroupBy, Sort, Join); disk I/O (TextFileSink); data movement (GroupBy, Sort, Join); fixed per-job overhead (ReduceBy, Distinct, Sort, TextFileSink).
\item \hl{Not needed} (negligible for every operator): garbage collection.
\item Operators whose own cost is below measurement noise: Filter, Count, UnionAll (a constant or a per-row cost from the source/sink is enough).
\end{itemize}

\textbf{Pending:} Spark (cluster), PostgreSQL are not in the data used for this version of the report.
\section{Method}

\textbf{Measurement.} Each configuration (operator, input size, number of distinct keys, row width, selectivity, JVM and platform settings) runs in a fresh JVM. It executes two plans alternately after warm-up runs: a \emph{baseline} (source $\to$ parse $\to$ sink) and the \emph{operator plan} (the same with the operator inserted). The operator's cost is the difference of the two runs of a pair, in every metric; a configuration has 3--7 pairs. Metrics are read from the JVM and the operating system over the window from the first record to the end of the job, so Wayang's own optimisation is excluded. Pairs with a run measured at a reduced CPU clock or next to other busy processes are flagged by the profiler and left out here.

The \emph{fixed overhead} is not a column: runtime is fitted as $\text{fixed} + \text{per-unit}\times(\text{input rows}+\text{output rows})$ through the medians of the smallest and the largest 20\% of the configurations of the operator, and the fixed part is compared with the median added runtime.

\textbf{Rating.} For every resource and operator we compute (i) the \emph{signal}: the share of configurations whose median added amount is above the spread between pairs (IQR) and above a floor (1\,ms, 64\,KiB), and (ii) the \emph{magnitude} in the median configuration: for CPU and GC the share of the operator's added runtime (CPU time $/$ (wall time $\times$ threads)); for memory, disk and data movement bytes per input byte; for the fixed overhead its share of the median added runtime. \high~\emph{important}: signal $\geq$ 50\% and magnitude $\geq$ 0.30 (time) or 0.50 (bytes); \some~\emph{sometimes}: signal $\geq$ 20\% and magnitude $\geq$ 0.05, or the 90th percentile $\geq$ the important threshold; \low~\emph{negligible}: otherwise. A superscript $-$ means the operator \emph{reduces} the resource compared to its baseline (e.g.\ a filter sends fewer rows onward). A dot means the operator's added runtime is below noise in more than 80\% of its configurations, so no rating is meaningful.

\textbf{Input properties.} For every operator we compute the Spearman rank correlation $\rho$ between its added runtime and each property of the configuration (input rows, output rows, distinct keys, row width, selectivity, left$\times$right rows for binary operators). $|\rho|\geq 0.6$ counts as \emph{needed}, $0.3\leq|\rho|<0.6$ as \emph{weak}, below as \emph{not needed}.

\section{What this means for the cost model}
\begin{itemize}\itemsep2pt
\item \textbf{Java.} Predict CPU, disk I/O. Garbage collection can be left out or kept as a constant. A per-job fixed cost matters for TextFileSink.
\item \textbf{Spark (single node).} Predict CPU, memory, disk I/O, data movement, fixed per-job overhead. Garbage collection can be left out or kept as a constant. A per-job fixed cost matters for ReduceBy, GroupBy, Distinct, Sort, Join, Cartesian, TextFileSink.
\item \textbf{Inputs.} Use the properties marked needed in the matrices above per operator; properties with $|\rho|<0.3$ for an operator carry no usable signal for it. Output rows is often the strongest driver of filtering and grouping operators, but is unknown before execution: the model should receive Wayang's cardinality estimate for it.
\end{itemize}
\section{Limitations}
\begin{itemize}\itemsep2pt
\item On the Java platform an operator runs on one thread, so its CPU time equals its runtime: CPU is then the resource by construction, and the other resources decide only what \emph{else} must be predicted.
\item Ratings describe the configurations that were measured (inputs of $10^3$--$3\cdot10^6$ rows, synthetic data with one row layout); a resource rated negligible here can matter for much larger inputs.
\item An operator whose cost is below noise in most configurations is not ``unimportant'': it is cheap next to reading and parsing its input. Its cost can still add up in long pipelines.
\item Data movement for Spark on a single node is the shuffle volume written; only a cluster measures real network traffic between executors.
\item Energy and hardware counters (cycles, instructions) exist on macOS only and are not part of this analysis.
\end{itemize}
